The Missing Employee Access Control

TechCorp's Employee Management Portal identifies each employee record with a simple number in the URL. Investigate whether one employee can reach another employee's private profile just by changing that number.

Task 1 Briefing ▾

Alex has just wrapped up the investigation into the exposed employee file. Back at TechCorp, Sarah, the Security Team Lead, has another assignment.

Sarah: "We fixed the file exposure issue, but employees are still reporting something strange. Some users say they can see another employee's information just by changing a number in the URL. Find out how this is happening."

The Employee Management Portal stores a record for every staff member. Each record is identified by a numeric Employee ID, and the profile page puts that ID straight into the URL:

/profile/101

Alex is given a normal Employee account for the investigation. His job is to find out whether the portal actually checks that a logged-in employee is allowed to view the profile they requested — or whether it simply trusts the ID in the URL.

Sarah: "Knowing an ID is not the same as being allowed to use it. The server has to decide that — every single request."

Task 2 Mission 1 — Log In as an Employee ▾

Alex starts with the Employee account provided by Sarah.

username: alex
password: Alex@123

Your task

  1. Log in using the Employee account.
  2. Confirm that the login succeeds and you reach the Dashboard.
  3. Note the account you are authenticated as.
Task 3 Mission 2 — Inspect Your Own Profile ▾

From the Dashboard, open My Profile. This shows the record the portal stores about your own account.

Your task — look closely at the page and, importantly, at the address bar:

  • What URL does your profile load from?
  • Which part of that URL identifies which employee is shown?
  • What is your own Employee ID?

Question to think about: the profile URL ends in a number. Where does that number come from, and what would happen if it were different?

Task 4 Mission 3 — Follow the Evidence ▾

The profile URL contains a value that you, the client, control — the employee ID. Instead of assuming the server protects each record, Alex decides to test what the application does with that identifier.

Your task — use the address bar and your browser's developer tools to investigate:

  • Which exact number in the URL selects the profile?
  • Are there other valid employee IDs?
  • Does the server ever check that the record belongs to you?

💡 Don't guess the answer. Change the value and observe how the server responds.

Look at the profile URL carefully. It looks like /profile/101. The number at the end is the object being requested.
That number is the employee identifier, and it came from you (it's right there in the URL). Ask yourself what happens when the identifier changes — for example, from 101 to 102.
A secure portal would verify, on the server, that the logged-in user is authorised to view this specific record before returning it. If that check is missing, any valid ID you type will be shown to you — even one that isn't yours.
Task 5 Mission 4 — The Unlocked Record ▾

Alex is authenticated as a normal Employee, yet the portal identifies records with a value that any user can change. He decides to see whether the account can reach a profile that should belong to someone else.

Your task — starting from your own profile URL, investigate another employee's record by changing the identifier. Use only the provided lab environment.

Success condition — reach an employee profile that is not your own and find the flag hidden inside it.

Task 6 Mission 5 — Explain the Incident ▾

Alex reports his findings to Sarah.

Alex: "I was logged in as a normal employee, but the portal decided which record to show based only on the ID in the URL. It never checked that the record was mine."

Sarah asks Alex to prove that he understands what happened.

Answer the following (for your own notes):

  1. What vulnerability did you discover?
  2. What part of the URL controlled which employee profile was displayed?
  3. Were you authorised to access the other employee's profile?
  4. Whose profile did you reach, and what information was exposed?
  5. Which server-side check was missing?
  6. How should TechCorp prevent this?
Task 7 🏁 Final Challenge ▾

Complete the investigation with a short knowledge check.

🎓 What Alex Learned

🔗 Direct Object Reference
The application selected a record using an ID that the user fully controlled in the URL.

🛡️ Missing Authorization
The server never verified that the logged-in user was permitted to access that specific record.

⭐ Key Lesson: Knowing or changing an object's identifier does not grant permission to access it. Authorization must be checked server-side on every request.
